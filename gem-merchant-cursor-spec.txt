COMPLETE PRODUCT, UX, VISUAL, GAME ENGINE, MULTIPLAYER AND DEPLOYMENT SPECIFICATION

============================================================
1. PROJECT OBJECTIVE
============================================================

Build a polished browser-based multiplayer strategy board game inspired by the classic gem-collection and development-card genre.

The application should feel like a premium physical tabletop game converted into a modern desktop web experience.

The goal is NOT to build:
- a generic React card UI
- an admin dashboard
- a basic multiplayer demo
- a collection of HTML cards
- a mobile-first game
- a casino interface

The goal is to create a visually rich, intuitive, responsive and highly polished digital tabletop experience.

The player should feel that:

"I am sitting at a premium game table with physical cards, gemstones and opponents."

The game should be simple to understand but visually sophisticated.

IMPORTANT IP / ORIGINALITY REQUIREMENT

Do not copy:
- commercial board-game logos
- original artwork
- original card illustrations
- exact card layouts
- trademarked names
- trademarked branding
- scans/photos of physical cards
- proprietary UI assets

Use an original game identity.

The game can use similar high-level mechanics such as:
- collecting colored resources
- purchasing development cards
- permanent discounts
- reserved cards
- special characters/achievements
- victory points
- turn-based play

But the visual identity, terminology, artwork and implementation should be original.

If implementing a specific existing game's rules or card data, only use data that is legally available for the project. Keep the engine configurable so the rules and card dataset can be replaced independently from the UI.

============================================================

============================================================
69. GAME STATE PERSISTENCE
============================================================

Every valid action:

validate
   |
apply
   |
persist game state
   |
persist move
   |
broadcast

Use a safe persistence strategy.

If possible, use MongoDB transactions for related writes when the deployment supports them.

At minimum, make the server resilient to a failure between state and move persistence.

Do not broadcast a state that was never successfully persisted.

============================================================
70. GAME RECOVERY
============================================================

On server startup:

Find active games.

Restore their state.

Rebuild active game rooms.

Players should be able to reconnect.

Do not depend entirely on server RAM.

============================================================
71. MOVE HISTORY
============================================================

Store every valid action.

This provides:
- debugging
- replay
- audit
- support investigation
- future analytics

============================================================
72. MONGODB CONNECTION
============================================================

Create a reusable MongoDB connection module.

Do not create a new database connection for every request.

Use a connection pool.

Keep:

in environment variables.

Do not expose MONGODB_URI to the browser.

============================================================
73. MONGODB DOCUMENT SIZE
============================================================

Do not allow unlimited game history inside a single game document.

Keep current game state in the games collection.

Keep move history in gameMoves.

This prevents a game document from growing unnecessarily.

107. MOST IMPORTANT PRINCIPLE
============================================================

The game should have three distinct layers:

GAME RULES

The game engine knows what is allowed.

GAME STATE

The server knows what is happening.

PRESENTATION

The browser makes the game beautiful and easy to play.

Never mix these layers.

The final result should feel like:

      PHYSICAL BOARD GAME
              +
       MODERN WEB UI
              +
       REAL-TIME MULTIPLAYER
              +
       PREMIUM ANIMATION
              +
       SIMPLE CONTROLS

The user should never need to think about the underlying technology.

They should simply feel like they are playing a beautiful strategy board game.
